# Handoff (OPEN — decision requested): how should comparator reports be "regenerated"?

**Status:** OPEN. This is *not* a resolved-archive item — it is a decision request for the
Claude Chat session orchestrating the circuits re-qualification program (`v2.1-circuits`).
Not listed in `handoffs/README.md` (which is a resolved-only archive).

**Raised by:** Phase B (`circuits/comparators/`) of the circuits re-qualification program.
**Blocks:** only the comparator `.md` report *files*. The data layer (JSON results, saturation
orphan fix, `comparators_all.lib`, grade-change analysis) is unblocked and is being regenerated
regardless of this decision.

---

## The conflict

**Ground Rule 2** of the program brief states:

> Every report is regenerated by its library's own scripts, never hand-edited. Where a script
> writes no results file (the known `run_saturation.py` case), fixing it to write one is in scope.

and the Phase B scope line says the ICMR sign-off tables should "become **diffable**."

**But the comparator reports have no generator scripts.** Unlike `async_logic_design/`, which ships
`report.py` + `summary.py` that emit `REPORT.md` / `SUMMARY.md` from `results.json`, the comparator
directory's `.md` files are **hand-authored prose**: topology ASCII-art, design rationale, and
measured numbers typed inline. The only auto-generated artifact is `comparators_all.lib` (its own
header says so).

### Evidence

- Report files (9 total across 6 subdirs), all hand-authored:
  - `general_purpose/`: `README.md`, `CHARACTERIZATION.md`, `DESIGN_NOTES.md`, `SATURATION_SIGNOFF.md`
  - `general_purpose_1v8/`, `general_purpose_3v3/`, `rail_to_rail_1v8/`, `rail_to_rail_3v3/`,
    `rail_to_rail_5v0/`: `README.md` each
  - ("all six reports" in the brief = the 6 subdir `README.md`; GP-5V additionally carries the 3
    deeper docs.)
- `grep AUTOGEN|auto-generated|do not edit` across `comparators/**/*.md` → **one** hit, and it is
  `general_purpose/README.md:39` describing `comparators_all.lib`, *not* the report itself.
- The run scripts write **only** JSON: `run_comparators.py` / `run_rr.py` → `comparator_results.json`
  (`Path(...).write_text(json.dumps(rows))`). No `.md` is emitted anywhere.
- Numbers are embedded in prose and **the MC basis differs per report**: GP-5V cites "500-run Monte
  Carlo", the other five cite "200-run". A regeneration mechanism has to reconcile this.

So Ground Rule 2 cannot be satisfied literally today — the "library's own scripts" that would
regenerate these reports **do not exist**. Creating them is real work, and *how* to create them is
a maintainer-level fork.

---

## The three options (what I asked, and the trade)

| Option | Effort | Honors GR2? | Preserves hand-authored prose? |
|---|---|---|---|
| **A. Marker-delimited table injection** — write `report_refresh.py` that regenerates only the data tables + numeric spec lines from JSON, inside `<!-- AUTOGEN:… -->` fences; prose/diagrams untouched. | Medium | Yes (tables are script-generated + diffable) | Yes |
| **B. Full report generators** — per-subdir scripts emit the whole report from data + templated prose, like async's `report.py`. | High | Yes (fully) | No — all design prose must be re-encoded into templates; risk of losing nuance |
| **C. Update numbers in prose by hand** — treat JSON as the regenerated results file; hand-edit only the stale measured numbers in the existing `.md`. | Low | No — explicit override of GR2 | Yes |

**My recommendation: Option A.** It is the only option that satisfies both halves of the rule —
the sign-off tables become script-generated and diffable (what the brief explicitly wants), while
the hand-authored topology/design prose is preserved verbatim outside the AUTOGEN fences. It also
generalizes: the same `report_refresh.py` pattern can back-fill the async reports later if desired.

## Decision requested

1. Which option (A / B / C) for regenerating the comparator reports?
2. If A or B: confirm the AUTOGEN-fence / template convention is acceptable to add to these
   directories (it is a new file `report_refresh.py` per subdir, or one shared module).
3. Confirm the reconciliation for the differing MC basis in existing prose (GP-5V "500" vs others
   "200"): the re-run is uniform N=200, so the regenerated tables/spec-lines will read "200-run"
   everywhere — acceptable?

Once ruled, Phase B's report layer can be finished in a follow-up commit; the data layer is already
consistent with `v2-grounded`.
